# ระบบลงเวลาเข้า-ออกงานด้วยรูปถ่าย

เว็บแอปสำหรับให้พนักงาน **ถ่ายรูปสด** ตอนลงเวลาวันละ 4 ครั้ง
(เข้าเช้า → ออกพักเที่ยง → เข้าบ่าย → เลิกงาน) ระบบประทับ **วัน-เวลา-พิกัด** ลงบนรูป
เก็บลงฐานข้อมูล และออกรายงานสรุป **รายบุคคล / รายวัน / รายเดือน** พร้อม export Excel, CSV และพิมพ์เป็น PDF

- สเปกฉบับเต็ม (prompt ที่ใช้สร้างระบบนี้): [PROMPT.md](PROMPT.md)
- Stack: Next.js 15 (App Router) + TypeScript + Tailwind CSS + Supabase (Postgres + Storage)

| **หลังบ้าน** (จัดการ/รายงาน) | `/admin` เท่านั้น | PIN 6 หลัก (ค่าเริ่มต้น `123456`, ตั้งที่ `ADMIN_PIN`) |

เบอร์มือถือคือรหัสประจำตัวที่ใช้เข้าระบบ (ห้ามซ้ำกัน) กรอกแบบมีขีดหรือไม่มีก็ได้ ระบบตัดให้เหลือตัวเลขเอง
**พนักงานเปลี่ยนรหัสผ่านเองได้** ที่หน้า "ประวัติของฉัน" หรือที่ `/login/change-pin` จากหน้าล็อกอินโดยไม่ต้องเข้าระบบก่อน (ต้องกรอกรหัสเดิมยืนยัน) ·
ถ้าลืมรหัส แอดมินรีเซ็ตให้ได้ที่หน้าพนักงาน

เส้นทางย่อยของหลังบ้าน (`/admin/employees`, `/admin/reports/...`) เข้าตรงไม่ได้
ถ้ายังไม่ผ่าน PIN จะถูกส่งกลับมาที่ `/admin` เสมอ

**บัญชีพนักงานเริ่มต้นจาก seed.sql (รหัสผ่าน = `1234` — เปลี่ยนทันทีหลังใช้งานจริง)**

## 7. Deploy ขึ้น Cloudflare Workers

ระบบถูก deploy ไว้แล้วที่ **https://web-time-attendance.web-time-attendance.workers.dev**
(ใช้ [@opennextjs/cloudflare](https://opennext.js.org/cloudflare) แปลง Next.js เป็น Worker)

```bash
npm run cf:build
```

```bash
npm run cf:deploy
```

`npm run cf:deploy` เรียก [`scripts/cf-deploy.mjs`](scripts/cf-deploy.mjs) ซึ่งหา Cloudflare API token
ให้เองตามลำดับนี้ ไม่ต้องตั้ง environment variable เองทุกครั้ง

1. ตัวแปรสภาพแวดล้อม `CLOUDFLARE_API_TOKEN` (ถ้ามี ใช้ตัวนี้ก่อน)
2. บรรทัด `CLOUDFLARE_API_TOKEN=...` ในไฟล์ `.env.local`
3. ไฟล์ `token.txt` (ในโปรเจกต์ หรือโฟลเดอร์แม่) — บรรทัดที่ขึ้นต้นด้วย `cfut_`

สคริปต์ไม่พิมพ์ค่า token ออกหน้าจอและไม่คัดลอกไปเก็บที่อื่น
ถ้าหา token ไม่เจอจะบอกวิธีแก้เป็นภาษาไทยแล้วหยุด

**ค่า config:** ไม่ลับอยู่ใน [`wrangler.jsonc`](wrangler.jsonc) (`NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_PHOTO_BUCKET`, `TZ`)
ส่วนที่เป็นความลับตั้งเป็น secret (ตั้งไว้แล้ว ไม่ต้องทำซ้ำ):

```bash
npx wrangler secret put ADMIN_PIN
```

secret ที่ระบบใช้: `SUPABASE_SERVICE_ROLE_KEY`, `SESSION_SECRET`, `ADMIN_PIN`

> **ข้อควรระวัง:** เว็บนี้เปิดสาธารณะบนอินเทอร์เน็ต การป้องกันมีแค่ PIN
> ควรเปลี่ยน `ADMIN_PIN` จาก `123456` เป็นเลขที่เดายาก และเปลี่ยน PIN พนักงานจาก `1234`

2. ใส่ Environment Variables ตาม `.env.example` แล้ว Deploy

## โครงสร้างฐานข้อมูล (normalize แล้ว)

แต่ละประเภทข้อมูลอยู่คนละตาราง ผูกกันด้วย foreign key — ค่าหนึ่งค่าเก็บที่เดียว ไม่ซ้ำซ้อน

```
work_schedules ──┐                    departments ──┐
 (เวลาเข้า/ออกพัก/  │                     (ชื่อแผนก)      │
  เข้าบ่าย/เลิกงาน)  │                                  │
                 ▼                                  ▼
work_settings   branches ◄──────────────────── employees ──► positions
 (ค่าองค์กร +    (รหัส/ชื่อ/พิกัด/       branch_id      (ID, ชื่อ,       (ชื่อตำแหน่ง)
  กะเริ่มต้น)      รัศมี/กะที่ใช้)                      เบอร์โทร, PIN)
                     ▲                              │
                     └──── branch_id ── attendance_records ── holidays
                                        (การลงเวลา 4 ครั้ง/วัน + รูป)
```

| ตาราง | เก็บอะไร | ความสัมพันธ์ |
|---|---|---|
| `employees` | รหัสพนักงาน, ชื่อ, ชื่อเล่น, **เบอร์มือถือ (unique, ใช้ login)**, รหัสผ่าน (bcrypt), สิทธิ์ | → `branches`, `departments`, `positions` |
| `branches` | รหัสสาขา, ชื่อสาขา, **พิกัด lat/lng (วางลิงก์ Google Maps ได้)**, รัศมี, ที่อยู่, เบอร์โทร | → `work_schedules` |
| `work_schedules` | **เวลาเข้างาน / ออกพักเที่ยง / เข้างานบ่าย / เลิกงาน** + นาทีผ่อนผัน, โควตาพัก, OT, วันทำงาน | — |
| `departments` / `positions` | ชื่อแผนก / ชื่อตำแหน่ง | — |
| `work_settings` | ชื่อร้าน, บังคับ GPS, รัศมีเริ่มต้น, กะเริ่มต้น (แถวเดียว) | → `work_schedules` |
| `attendance_records` | การลงเวลา 4 ครั้ง/วัน + รูป + พิกัด | → `employees`, `branches` |
| `holidays` / `audit_logs` | วันหยุด / ประวัติการแก้ไขของแอดมิน | — |

**หน้าจอ setup**: `/admin/setup` แก้ทุกตารางค่าหลักได้จากที่เดียว (กะทำงาน, แผนก, ตำแหน่ง)
พร้อมแสดงจำนวนที่ถูกใช้งานอยู่ และห้ามลบข้อมูลที่ยังมีคนใช้

**ตัวอย่างการไม่ซ้ำซ้อน**: เวลาเข้างานเก็บที่ `work_schedules` ที่เดียว
สาขาไหนใช้เวลาเดียวกันก็ชี้มาที่กะเดียวกัน แก้ครั้งเดียวเปลี่ยนทุกสาขาที่ใช้กะนั้น

## ระบบหลายสาขา

- หน้า **สาขา** เพิ่ม/แก้/ลบสาขาได้ (ลบได้เมื่อไม่มีพนักงานอยู่ในสาขานั้น)
- แต่ละสาขากำหนด **กะทำงาน** และ **พิกัด+รัศมี GPS** ของตัวเองได้ — ช่องที่เว้นว่างจะใช้ค่ากลางจากหน้าตั้งค่า
- **พิกัดสาขาวางจาก Google Maps ได้เลย** ช่องเดียวจบ รองรับทั้ง
  `13.756331, 100.501765` (คลิกขวาบนแผนที่ → คลิกที่ตัวเลขเพื่อคัดลอก) และลิงก์เต็มแบบ
  `https://www.google.com/maps/place/.../@13.75,100.50,17z/data=...!3d13.756331!4d100.501765`
  ระบบเลือกพิกัดหมุดจริง (`!3d!4d`) ไม่ใช่จุดกึ่งกลางจอ · แต่ละสาขามีปุ่ม **📍 เปิดแผนที่** ให้ตรวจซ้ำได้
  (ลิงก์ย่อ `maps.app.goo.gl` อ่านไม่ได้ ให้เปิดลิงก์ก่อนแล้วคัดลอกพิกัดมาวาง)
- พนักงานผูกกับสาขา และการลงเวลาแต่ละครั้ง **บันทึกสาขา ณ ตอนนั้น** ไว้ด้วย รายงานย้อนหลังจึงไม่เพี้ยนแม้ย้ายสาขาภายหลัง
- รายงานทั้ง 3 แบบและ dashboard กรองตามสาขาได้ และมีคอลัมน์สาขาในไฟล์ export

## ตารางเวร (พนักงานที่สลับกะ)

สำหรับธุรกิจที่ทำงานเป็นกะ (โรงแรม: กะเช้า/บ่าย/ดึก) และคนหนึ่งไม่ได้อยู่กะเดิมทุกวัน

- **แยก 2 ชั้น ไม่เก็บซ้ำ**: "นิยามกะ" (`work_schedules` — กะเช้า 07:00–16:00, กะดึก 22:00–07:00 …)
  กับ "ตารางเวร" (`shift_assignments` — คนนี้ วันนี้ ใช้กะไหน หรือ **หยุดเวร**) เก็บ **แถวละ 1 คน 1 วัน**
  เพราะโรงแรมสลับ/แลกเวรกันทีละวัน แก้ 1 วัน = แก้ 1 แถว
- **ลำดับการเลือกกะเพื่อคำนวณ**: ตารางเวรของคนนั้นวันนั้น → กะของสาขา → กะเริ่มต้นของบริษัท
  พนักงานที่ทำเวลาเดิมทุกวัน (บัญชี แม่บ้าน) **ไม่ต้องจัดเวร** ระบบใช้กะสาขาเหมือนเดิม
- หน้า **แอดมิน → ตารางเวร** (`/admin/roster`): ตาราง พนักงาน × วันที่ (รายสัปดาห์/รายเดือน)
  จัดเป็นชุด (หลายคน × ช่วงวันที่ × เฉพาะวันในสัปดาห์), คลิกช่องแก้ทีละวัน (ใส่หมายเหตุ "แลกเวรกับ…" ได้),
  คัดลอกจากสัปดาห์ก่อน, ล้างช่วง (ต้องติ๊กยืนยัน) — ทุกอย่างลง `audit_logs`
- **กะข้ามเที่ยงคืน** (เลิกงาน ≤ เข้างาน เช่น 22:00–07:00): สาย/กลับก่อน/OT คำนวณจาก timestamp จริง
  และการกดออกงานตอนเช้าผูกกับ **วันที่เริ่มกะ** (เมื่อวาน) โดยอัตโนมัติ ถ้ายังไม่ได้กดออกและยังไม่เลยเวลาเลิกกะเกิน 4 ชม.
- หน้าลงเวลาแสดง "กะวันนี้: กะบ่าย 14:00–23:00" · หน้า **ประวัติของฉัน** แสดงตารางเวร 7 วันข้างหน้า
- รายงานมีคอลัมน์ **กะ** และสถานะ **หยุดเวร** (นับแยก ไม่ใช่ขาดงาน) · ลบกะที่ยังถูกจัดเวรอยู่ไม่ได้

## งานนอกสถานที่ / งานนอกเวลา (ออกบูธ, ส่งรถ, งานพิเศษ)

พนักงานประจำสาขาชุดเดียวกัน บางวันต้องออกไปทำงานข้างนอก ระบบแยกเป็น 2 กลไกตามว่างานนั้น "แทน" หรือ "เพิ่มจาก" งานปกติ

| สถานการณ์ | ทำอย่างไร | การลงเวลา | รายงาน |
|---|---|---|---|
| ไปประจำบูธ **ทั้งวัน** แทนเข้าสาขา | ตารางเวร → ช่อง **สถานที่** (📍) | 4 ครั้งตามปกติ แต่ GPS ตรวจกับพิกัดบูธ | วันทำงานปกติ + แสดง 📍 สถานที่ |
| ออกบูธ/งานพิเศษ **นอกเวลา** (เย็น, วันหยุด) | **ภารกิจ** ที่ "นับชั่วโมง" | กดเริ่ม → จบ พร้อมรูป + GPS | คอลัมน์ **งานพิเศษนอกสถานที่** แยกจาก OT |
| ส่งรถ / ออกไปข้างนอก **ระหว่างเวลางาน** | **ภารกิจ** ที่ "ไม่นับชั่วโมง" | เริ่ม → จบ เป็นหลักฐานว่าไปถึงจริง | แสดงในรายงานงานนอกสถานที่ ไม่บวกชั่วโมง |

- **สถานที่ปฏิบัติงาน** (`work_sites`) ตั้งที่ ตั้งค่าข้อมูลหลัก — ชื่อ พิกัด (วางลิงก์ Google Maps ได้) รัศมี · แยกจากสาขา ใช้ร่วมกันทั้งตารางเวรและภารกิจ
- **ประเภทงาน** (`field_task_types`) ออกบูธ/ส่งรถ/อบรม/อื่น ๆ พร้อมค่าเริ่มต้นว่านับชั่วโมงหรือไม่ (แก้รายภารกิจได้)
- หน้า **แอดมิน → งานนอกสถานที่** (`/admin/field`): สร้างภารกิจ (ประเภท ชื่อ สถานที่หรือพิมพ์เอง วันที่ เวลาแผน สมาชิกหลายคน),
  แก้ไข/ยกเลิก/ลบ, **บันทึกเวลาให้** เมื่อพนักงานลงเวลาไม่ได้ (ติดธง "แก้ไข") — ทุกอย่างลง `audit_logs`
- หน้า **ตารางบูธ** (`/admin/field/roster`): ตาราง พนักงาน × วันที่ แบบเดียวกับตารางเวร สำหรับจัดว่าใครประจำบูธไหนวันไหน
  (คนละคนแต่ละวันได้) — จัดเป็นชุด (หลายคน × ช่วงวัน × เฉพาะวันในสัปดาห์), คลิกช่องเพิ่ม/เอาออกทีละวัน,
  คัดลอกจากสัปดาห์ก่อน, ล้างช่วง · คนที่อยู่บูธเดียวกัน วันเดียวกัน เวลาเดียวกัน ถูกรวมเป็น**งานเดียว**
  (`findOrCreateFieldTask`) ไม่แตกเป็นงานละคน · ช่องแสดง ✓ เสร็จ / ● กำลังทำ / ! ไม่ได้กดจบ
- หน้าลงเวลาของพนักงานมีการ์ด **งานนอกสถานที่** (ปุ่มเริ่ม/จบ) และปุ่ม **+ เริ่มงานเอง** สำหรับงานฉุกเฉินอย่างส่งรถ
  (พนักงานเลือกประเภท + สถานที่หรือพิมพ์เอง → ถ่ายรูปเริ่มงานทันที หัวหน้าเห็นในหลังบ้าน)
- การลงเวลาภารกิจเก็บใน `field_punches` แยกจาก `attendance_records` จึงมีหลายงานในวันเดียวได้โดยไม่ชนกับ 4 ครั้งปกติ
- GPS ของภารกิจ: สถานที่ที่มีพิกัด → ตรวจรัศมีเมื่อองค์กรบังคับ GPS · ปลายทางที่พิมพ์เอง → บันทึกพิกัดจริงอย่างเดียว
- **รายงานงานนอกสถานที่** (`/admin/reports/field`) + Excel/CSV · รายเดือนมีคอลัมน์ "งานพิเศษนอกสถานที่" · `/me` แสดงงานของตัวเอง

## สิทธิ์เข้าหน้าจัดตาราง (ไม่ต้องใช้ PIN หลังบ้าน)

หน้า **ตารางเวร** (`/admin/roster`), **ตารางบูธ** (`/admin/field/roster`), **งานนอกสถานที่** (`/admin/field`)
และ **รายงานงานนอกสถานที่** (`/admin/reports/field`) เข้าได้ 2 ทาง

| ทางเข้า | ทำอะไรได้ |
|---|---|
| ผ่าน PIN หลังบ้าน | ทุกอย่าง (เหมือนเดิม) |
| ล็อกอินพนักงาน + สิทธิ์รายเมนูจากระบบส่วนกลาง | ตามสิทธิ์: **อ่าน** = ดูตาราง · **เพิ่ม** = จัดเป็นชุด/คัดลอก · **แก้ไข** = แก้ทีละช่อง/บันทึกเวลาให้ · **ลบ** = ล้างช่วง/ลบงาน |

- ค่าเริ่มต้นตามระดับ (migration 0026): admin/ผู้ช่วย ทำได้ทุกอย่าง · **supervisor อ่าน/เพิ่ม/แก้** (ไม่ลบ) · user ไม่เห็นหน้าจัดตาราง
  ปรับรายคนได้ที่ ระบบส่วนกลาง → สิทธิ์ผู้ใช้ (เมนู `ATT_ROSTER`, `ATT_FIELD_ROSTER`, `ATT_FIELD`, `ATT_REP_FIELD`)
- ผู้ที่เข้าด้วยสิทธิ์รายเมนูเห็นเฉพาะ **บริษัท/สาขาในขอบเขตของตัวเอง** และปุ่มที่ไม่มีสิทธิ์จะไม่แสดง
  (ฝั่ง server ตรวจซ้ำทุก action ด้วย `requireMenuAccess` ใน [att-access.ts](src/lib/att-access.ts))
- แถบเมนูของคนกลุ่มนี้แสดงเฉพาะหน้าที่มีสิทธิ์อ่าน + ลิงก์กลับหน้าลงเวลา/รวมโปรแกรม · หน้าอื่นใต้ `/admin` ยังต้องใช้ PIN ตามเดิม
- ทุกการแก้ไขบันทึก `audit_logs` พร้อม `actor_id` ของผู้ใช้ (ผ่าน PIN = null)

## ออกไปทำธุระระหว่างวัน

หลังเข้างานแล้ว พนักงานออกไปทำธุระข้างนอกได้ แต่ต้องกด **ออกไปทำธุระ** และ **กลับเข้างาน** ทุกครั้ง (ถ่ายรูป + GPS เหมือนการลงเวลาปกติ)

- ออก-กลับได้ **หลายรอบต่อวัน** เก็บที่ตาราง `errand_punches` แยกจาก `attendance_records`
  (ตารางเดิมมีข้อจำกัด 1 วัน = ประเภทละครั้งเดียว)
- **โควตาเดียวกับพักเที่ยง**: เวลาพักเที่ยง + เวลาธุระทุกรอบ รวมกันไม่เกิน `break_allow_minutes` (ปกติ 60 นาที)
  ส่วนที่เกินนับเป็น **พักเกินเวลา** และถูกหักออกจากชั่วโมงทำงาน — นำไปหักค่าจ้างได้
- ตัวอย่าง: พักเที่ยง 30 + ธุระ 20 + ธุระ 50 = 100 นาที → เกิน 40 นาที · ชั่วโมงทำงาน = 9 ชม. − 100 นาที = 7.33 ชม.
- วันที่ **ไม่ได้ลงเวลาพักเที่ยง** ถือว่าใช้เต็มโควตาตามกฎเดิม การออกธุระจึงเกินทันที
- กติกาการกด: ต้องเข้างานแล้ว · ยังไม่เลิกงาน · ไม่ได้อยู่ระหว่างพักเที่ยง · ออกซ้ำโดยไม่กดกลับไม่ได้
  (รอบที่ยังไม่กดกลับ ยังไม่ถูกนับเวลา แต่หน้าจอจะค้างปุ่ม "กลับเข้างาน" ไว้)
- หน้าลงเวลามีการ์ดสรุป "ใช้เวลาส่วนตัวไปแล้ว X / 60 นาที" พร้อมรายการแต่ละรอบและเหตุผล
- รายงานทุกแบบมีคอลัมน์ **ธุระ (นาที)** และไฟล์ export มี ธุระ / จำนวนครั้ง / เวลาส่วนตัวรวม
- แอดมินแก้เวลาออก-กลับ หรือลบธุระทั้งรอบได้ที่หน้า **แก้ไขเวลาย้อนหลัง** (`/admin/records/...`)

## จับคู่รหัสเงินเดือน (payroll) กับรหัสระบบลงเวลา

ระบบเงินเดือนใช้รหัสคนละชุดกับระบบลงเวลา (เช่น เคทูฯ ใช้ `K2009` / เกรียงไกรฯ ใช้ `002`)
เก็บไว้ที่ `employees.payroll_code` — พนักงาน 1 คนสังกัด 1 บริษัท จึงมีรหัสเงินเดือนชุดเดียว

- หน้า **แอดมิน → จับคู่รหัสเงินเดือน** (`/admin/payroll-map`)
  - ตารางแยกตามสาขา คีย์รหัสในช่องแล้วกด **บันทึกรหัสที่แก้ทั้งหมด** (บันทึกเฉพาะช่องที่แก้ · ล้างช่องว่าง = เอารหัสออก)
  - กรอง **เฉพาะที่ยังไม่จับคู่** เพื่อไล่คีย์คนที่เหลือ · มีตัวนับ จับคู่แล้ว/ยังไม่จับคู่
  - **วางข้อมูลจาก Excel** ก๊อปคอลัมน์ รหัส · ชื่อ · ชื่อเล่น มาวาง ระบบจับคู่ตามชื่อให้เอง
    (ตรงเป๊ะ → ต่างแค่วรรณยุกต์ → ชื่อต้น+ชื่อเล่นตรง) จับคู่เฉพาะที่ **ตรงคนเดียว** ที่เหลือรายงานกลับให้คีย์เอง
  - เตือนเมื่อรหัสซ้ำกันภายในบริษัทเดียวกัน (คนละบริษัทใช้เลขซ้ำได้ ถือว่าคนละชุด)
- ตรรกะเทียบชื่อไทยอยู่ที่ [thai-name.ts](src/lib/thai-name.ts) มีเทสต์ครอบ — รองรับคำนำหน้าหลายแบบ,
  `เเ` ที่พิมพ์แทน `แ`, วรรณยุกต์ต่าง (อุ่ม/อุ้ม) และนามสกุลสะกดต่าง (นาคสมพันธุ์/นาคสมพันธ์)
- **รายงานทุกแบบแสดงรหัสทั้งสองชุด**: ตารางรายงานมีคอลัมน์ รหัสลงเวลา + รหัสเงินเดือน ·
  รายเดือนแสดงเป็น `E045 / 012 · ชื่อ` · ไฟล์ export มีทั้งสองคอลัมน์พร้อมชื่อบริษัทและสาขา

## คลิกกล่องสรุปเพื่อกรอง และแก้เวลาจากรายงาน

ในหน้า **รายงานรายวัน**

- กล่องสรุป **ลงเวลาไม่ครบ · ขาดงาน · มาสาย · พักเกินเวลา** คลิกได้ ระบบจะกรองตารางเหลือเฉพาะกลุ่มนั้น
  (คลิกกล่องเดิมซ้ำ = ล้างตัวกรอง · ตัวกรองอยู่ใน URL `?flag=late` จึงส่งลิงก์ต่อให้คนอื่นดูได้)
- **คลิกที่ชื่อพนักงาน** เพื่อไปหน้าแก้ไขเวลาเข้า-ออกของคนนั้นในวันนั้นทันที
  (ชื่อจะเป็นลิงก์เฉพาะคนที่มีสิทธิ์อ่านเมนู "แก้ไขเวลาย้อนหลัง")

## ให้ฝ่ายบุคคลแก้เวลาได้ โดยไม่ต้องใช้ PIN

หน้ารายงาน (รายวัน/รายเดือน/รายบุคคล) และ **แก้ไขเวลาย้อนหลัง** (`/admin/records/...`)
ใช้ประตูคู่แบบเดียวกับตารางเวร: ผ่าน PIN หลังบ้าน **หรือ** ล็อกอินปกติแล้วมีสิทธิ์รายเมนู

| สิทธิ์ในเมนู "แก้ไขเวลาย้อนหลัง" | ทำอะไรได้ |
|---|---|
| อ่าน | เปิดดูหน้าแก้ไข และชื่อพนักงานในรายงานกลายเป็นลิงก์ |
| เพิ่ม / แก้ไข | แก้เวลาเข้า-ออก เพิ่มรายการที่ลืมลง และแก้เวลาธุระ |
| ลบ | ลบรายการลงเวลา หรือลบทั้งวัน |

- ค่าเริ่มต้น (migration 0040): admin/ผู้ช่วย ทำได้ทุกอย่าง · supervisor อ่าน/เพิ่ม/แก้ไข (ไม่ลบ) · user ไม่เห็น
- ฝ่ายบุคคลที่ไม่ได้อยู่ในระดับเหล่านั้น ให้กำหนดเป็นรายคนที่ **ระบบส่วนกลาง → สิทธิ์ผู้ใช้**
  และอย่าลืมกำหนด **ขอบเขตสาขา** ให้ด้วย (ติ๊ก "ทุกสาขา" หรือเลือกสาขาที่ดูแล) ไม่งั้นจะเห็นตารางว่าง
- ผู้ที่มีสิทธิ์อ่านแต่ไม่มีสิทธิ์แก้ไข จะเห็นหน้าเป็นแบบอ่านอย่างเดียว ปุ่มแก้/ลบถูกซ่อน
  และ server ตรวจซ้ำทุก action (ซ่อนปุ่มอย่างเดียวไม่พอ)
- **ข้อควรรู้**: 0009 เคยตั้งให้ทุกระดับรวมถึง `user` อ่านเมนูรายงานได้ ตอนนั้นไม่มีผลเพราะหน้าถูกล็อกด้วย PIN
  migration 0040 จึงปิดสิทธิ์อ่านรายงานของระดับ `user` ไว้ ไม่งั้นพนักงานทั่วไปจะเห็นเวลาเข้า-ออกของทุกคน

## จัดกลุ่มรายงานตามบริษัท / สาขา

รายงาน **รายวัน** และ **รายเดือน** มีช่อง **จัดกลุ่ม**: ไม่จัดกลุ่ม · แยกตามสาขา · แยกตามบริษัท

- รายวัน: แยกเป็นการ์ดต่อกลุ่ม แต่ละกลุ่มมียอดรวมของตัวเอง (มาทำงาน/สาย/ขาด/ลงไม่ครบ/พักเกิน/ชม.รวม)
- รายเดือน: ตารางเดียวคอลัมน์วันที่ตรงกันทั้งหน้า คั่นด้วยแถวหัวข้อกลุ่ม

## กฎการคำนวณโดยสรุป

- **สาย** = เวลาเข้าจริง − เวลาเข้ามาตรฐาน − นาทีผ่อนผัน
- **กลับก่อน** = เวลาเลิกมาตรฐาน − เวลาออกจริง − นาทีผ่อนผัน
- **เวลาพัก** = เข้าบ่าย − ออกพัก (ถ้าลงไม่ครบใช้โควตา 60 นาที)
  พักกลางวัน **ยืดหยุ่น** ออก-เข้าเวลาใดก็ได้ ไม่นับสาย แต่ **พักเกินโควตาจะถูกหักและติดธง**
- **เวลาส่วนตัว** = เวลาพัก + เวลาออกไปทำธุระทุกรอบ · **พักเกิน** = เวลาส่วนตัว − โควตา
- **ชั่วโมงทำงาน** = (เลิกงาน − เข้างาน) − เวลาส่วนตัวที่หัก
- **OT** = เวลาออกจริง − เวลาเลิกมาตรฐาน − นาทีผ่อนผัน OT (เปิด/ปิดได้)
- **สถานะวัน**: ครบ / ลงไม่ครบ / ขาดงาน / วันหยุด / หยุดเวร

ค่าทั้งหมดปรับได้ที่หน้า **แอดมิน → ตั้งค่า** และมีผลกับรายงานย้อนหลังทันที

## ความปลอดภัยที่ระบบทำให้

- เวลาที่บันทึกใช้ **นาฬิกาของเซิร์ฟเวอร์** เสมอ ไม่เชื่อเวลาเครื่องพนักงาน
- หน้าถ่ายรูป **ไม่มีปุ่มเลือกไฟล์** ใช้ได้เฉพาะกล้องสด และ server รับเฉพาะ JPEG ≤ 3MB
- ห้ามลงเวลาซ้ำช่วงเดิม (unique key ระดับฐานข้อมูล) และต้องลงตามลำดับ 1→2→3→4
- บังคับ GPS ในรัศมีที่กำหนดได้ (คำนวณระยะด้วยสูตร Haversine)
- รูปเก็บใน bucket **private** ดูได้ผ่าน signed URL อายุ 10 นาที และพนักงานดูได้เฉพาะรูปตัวเอง
- PIN เก็บเป็น bcrypt hash, ผิด 5 ครั้งล็อก 5 นาที, session เป็น JWT ใน httpOnly cookie 12 ชม.
- ทุกการแก้ไขย้อนหลังของแอดมินถูกบันทึกใน `audit_logs`

# โมดูลที่ 2: ระบบกิจกรรมการตลาด (`/marketing`)

ระบบบันทึกการจัดกิจกรรมการตลาด และคุมการเบิกเงินค่าส่งเสริมการขายกับบริษัทรถ
อยู่ในโปรเจกต์เดียวกัน ใช้ฐานข้อมูล Supabase และ Worker ตัวเดียวกับระบบลงเวลา
แต่แยกตารางออกจากกันทั้งหมด (ขึ้นต้นด้วย `mkt_`)

**เข้าใช้งานที่** `/marketing` — ต้องล็อกอินด้วย **เบอร์มือถือ + รหัสผ่าน** ชุดเดียวกับระบบลงเวลา
(บัญชีเดียวใช้ได้ทั้งสองระบบ ไม่ต้องจำรหัสสองชุด)

เปิดหน้าไหนของโมดูลนี้โดยยังไม่ล็อกอิน ระบบจะพาไปหน้า `/login` แล้ว**พากลับมาหน้าเดิม**ให้อัตโนมัติหลังล็อกอินสำเร็จ

## หน้าจอ

| หน้า | ทำอะไร |
|---|---|
| `/marketing` | หน้าแรก สรุปยอดรวมและกิจกรรมล่าสุด |
| `/marketing/activities` | 1. บันทึกงานกิจกรรม — เลขที่ (ออกอัตโนมัติ), วันที่, ชื่อ, ประเภท, บริษัทที่ขอเบิก, ผู้จัดทำ, รูปสูงสุด 10 รูป, memo, ยอดขอเบิก/อนุมัติ/ได้รับ, สถานะ |
| `/marketing/submit` | 2. บันทึกส่งเรื่องเบิกเงิน — ดึงข้อมูลจากหน้าจอ 1 มาแสดง แล้วบันทึกผู้ส่ง วันที่ส่ง เลขไปรษณีย์ รูปจดหมาย และรูปใบตอบรับ |
| `/marketing/receive` | 3. บันทึกรับเงิน — ผู้บันทึก วันที่รับ เลขที่ใบเสร็จ จำนวนเงินที่ได้รับจริง |
| `/marketing/setup` | 4. ค่าเริ่มต้น — พนักงาน / บริษัทที่ขอเบิก / ประเภทกิจกรรม (ID + ชื่อ) |
| `/marketing/search` | 5. สอบถาม — กรองตามสถานะ ช่วงวันที่ บริษัท ประเภท ผู้จัดทำ คำค้น + ดาวน์โหลด Excel/CSV |
| `/marketing/dashboard` | 6. Dashboard — กราฟยอดรายเดือน รายบริษัท และรายประเภทกิจกรรม |

## สถานะ 2 ชุด (ตามสเปก)

- **สถานะเอกสาร**: `ใช้งาน` / `ยกเลิก` — ตั้งเองที่หน้าจอ 1 (ใบที่ยกเลิกจะไม่ถูกนำไปรวมยอด)
- **สถานะการเบิก**: `ทำเรื่องตั้งเบิก` → `ส่งเบิกแล้ว` → `รับเงินแล้ว`
  ระบบเปลี่ยนให้เองเมื่อบันทึกหน้าจอ 2 และ 3 ผู้ใช้แก้ตรง ๆ ไม่ได้
  (คำนวณจาก `computeFlowStatus()` ใน `src/lib/marketing.ts` และมี `refreshFlowStatus()`
  ใน `src/lib/marketing-db.ts` เป็นผู้เขียนค่าลงฐานข้อมูลเพียงตัวเดียว)

## Memo โครงการ (หน้าจอ 7 และ 8)

Memo คือใบข้อตกลง/โครงการกับบริษัทรถ ที่ครอบใบกิจกรรมหลายใบและมีกำหนดระยะเวลาของตัวเอง

| หน้า | ทำอะไร |
|---|---|
| `/marketing/memos` | 7. บันทึก Memo — เลขที่ (ออกอัตโนมัติ `MEMO-2569-0001`), วันที่, บริษัทที่ขอเบิก, รายละเอียด, กำหนดระยะเวลาตั้งแต่-ถึง, ผู้บันทึก, ไฟล์แนบสูงสุด 20 ไฟล์ |
| `/marketing/memos/status` | 8. บันทึกเปลี่ยนสถานะ — เลือก Memo แล้วบันทึกสถานะใหม่ วันที่เปลี่ยน ผู้บันทึก และหมายเหตุ พร้อมแก้ไขข้อมูลของหน้าจอ 7 ได้ในหน้าเดียวกัน |

**สถานะ 5 ขั้น:** ยังไม่ได้ตั้งเบิก → ทำเรื่องตั้งเบิกแล้วบางส่วน → ได้รับเงินบางส่วน → ได้รับครบแล้ว → จบโครงการแล้ว

ทุกครั้งที่เปลี่ยนสถานะ ระบบเก็บลงตาราง `mkt_memo_status_logs` ไม่ทับของเดิม
ดูย้อนหลังได้ว่าใครเปลี่ยนอะไรเมื่อไหร่ · `changeMemoStatus()` ใน `src/lib/memo-db.ts`
เป็นผู้เขียนสถานะเพียงตัวเดียว เขียนทั้งสถานะปัจจุบันและแถวประวัติพร้อมกัน

Memo ยังโผล่ในหน้า **5. สอบถาม** (แท็บ Memo แยกจากใบกิจกรรม พร้อม export Excel/CSV)
และหน้า **6. Dashboard** (สรุปจำนวนตามสถานะ + กราฟจำนวน Memo ตามบริษัท)

### ไฟล์แนบเก็บคนละถังกับรูปลงเวลา

ถัง `attendance-photos` ตั้งไว้รับเฉพาะ `image/jpeg` ขนาดไม่เกิน 3 MB
ไฟล์แนบของ Memo จึงใช้ถัง **`marketing-files`** แยกต่างหาก (สร้างโดย migration `0008`)

เป็น private เหมือนกัน เปิดดูผ่าน signed URL ที่ออกจาก server เท่านั้น (`/api/marketing/file`)
ลบ Memo แล้วไฟล์ในถังถูกลบตามด้วย

| ตาราง | เก็บอะไร |
|---|---|
| `mkt_memos` | ใบ Memo + สถานะปัจจุบัน |
| `mkt_memo_files` | ไฟล์แนบ (เส้นทางไฟล์ ชื่อไฟล์เดิม ชนิด ขนาด) |
| `mkt_memo_status_logs` | ประวัติการเปลี่ยนสถานะทุกครั้ง |
| `v_mkt_memos` | view รวมข้อมูลสำหรับหน้ารายการ/สอบถาม/dashboard |


## การเข้าระบบและสิทธิ์

ทุกหน้าและทุก API ของโมดูลนี้ต้องล็อกอินก่อน กันไว้ 2 ชั้น:

1. `src/middleware.ts` — กัน `/marketing/*` และ `/api/marketing/*` ตั้งแต่ชั้น edge
2. `src/app/marketing/layout.tsx` เรียก `requireUser()` และ API แต่ละตัวเช็ค session ซ้ำอีกที

พนักงานที่ล็อกอินได้ทุกคนใช้โมดูลนี้ได้ (ไม่ต้องเป็นแอดมิน) — เพิ่ม/แก้บัญชีที่หน้า `/admin/employees` ของระบบลงเวลา

ผูกไว้แล้วเวลาคนนั้นล็อกอินเข้ามา ช่องผู้บันทึกในหน้าจอ 1/2/3 จะเลือกชื่อให้เองอัตโนมัติ (ยังเปลี่ยนเองได้)

# โมดูลที่ 3: ระบบส่วนกลางขององค์กร (`/core`)

รวมการตั้งค่าระดับองค์กรไว้ที่เดียว: **บริษัท → สาขา → ผู้ใช้งาน → สิทธิ์ → ทะเบียนโปรแกรม**
องค์กรเดียวมีได้หลายบริษัท แต่ละบริษัทมีได้หลายสาขา และผู้ใช้แต่ละคนถูกกำหนดได้ว่า
เข้าทำงานบริษัทไหน สาขาไหน ใช้โปรแกรมอะไร และทำอะไรได้บ้างในแต่ละหน้าจอ

## หน้าจอ

| หน้าจอ | URL | ทำอะไร |
|---|---|---|
| ภาพรวม | `/core` | นับบริษัท/สาขา/ผู้ใช้/โปรแกรม และผู้ใช้แยกตามระดับ |
| 1. ตั้งค่าบริษัท | `/core/companies` | รหัสบริษัท ชื่อบริษัท ที่อยู่ เลขผู้เสียภาษี สถานะ |
| 2. ตั้งค่าสาขา | `/core/branches` | รหัสสาขา ชื่อสาขา ที่อยู่ เบอร์โทร พิกัด รัศมี กะทำงาน และบริษัทที่สังกัด |
| 3. กำหนดผู้ใช้งาน | `/core/users` | User ID ชื่อผู้ใช้ รหัสผ่าน สถานะ (ใช้งานได้/ยกเลิก) และติ๊กเลือกโปรแกรมที่ใช้งานได้จากในตารางเลย |
| 3.1 สิทธิ์รายคน | `/core/users/<id>` | บริษัท/สาขาที่เข้าได้ · โปรแกรมที่ใช้ได้ · สิทธิ์ อ่าน/เพิ่ม/แก้ไข/ลบ รายเมนู · ตั้งรหัสผ่านใหม่ |
| 4. กำหนดสิทธิ์เมนูในโปรแกรม | `/core/program-rights` | เลือกโปรแกรม → เห็นเฉพาะคนที่มีสิทธิ์เข้า (ตามเมนู 5) → เลือกคน → ติ๊กว่าเข้าเมนูไหนได้ อ่าน/เพิ่ม/แก้ไข/ลบ อะไรได้ + ปุ่มคัดลอกให้ทุกคน / รีเซ็ตทั้งโปรแกรม |
| 4.1 ค่าเริ่มต้นตามระดับ (แม่แบบ) | `/core/levels` | ค่าตั้งต้นของ admin / ผู้ช่วย admin / หัวหน้างาน / ผู้ใช้ทั่วไป — ใช้เมื่อยังไม่ได้กำหนดเฉพาะราย |
| 5. กำหนดผู้ใช้งานโปรแกรม | `/core/program-users` | เลือกโปรแกรม แล้วเพิ่ม-ลด user ที่ใช้โปรแกรมนั้นได้ทั้งชุด + ปุ่ม "ให้สิทธิ์ทุกคน" |
| 6. ทะเบียนโปรแกรม | `/core/programs` | รหัสโปรแกรม ชื่อโปรแกรม สถานะ และเมนู/หน้าจอของแต่ละโปรแกรม |

หน้ารวมโปรแกรม `/apps` คือหน้าแรกหลังล็อกอิน แสดงเฉพาะโปรแกรมและเมนูที่คนนั้นมีสิทธิ์อ่านจริง ๆ

## กลุ่มระดับการทำงาน (4 ระดับ)

| ระดับ | ค่าเริ่มต้นที่ seed ไว้ |
|---|---|
| `admin` ผู้ดูแลระบบ | ได้ทุกสิทธิ์ทุกเมนูเสมอ (ฮาร์ดโค้ดไว้ กันแอดมินล็อกตัวเองออก) |
| `assistant_admin` ผู้ช่วยผู้ดูแลระบบ | อ่าน/เพิ่ม/แก้ไข ได้ทุกเมนู แต่ **ลบไม่ได้** |
| `supervisor` หัวหน้างาน | อ่านได้ทุกเมนู · เพิ่ม/แก้ไขได้เฉพาะหน้าจอบันทึกที่ไม่ใช่ระบบส่วนกลาง |
| `user` ผู้ใช้งานทั่วไป | เหมือนหัวหน้างาน แต่มองไม่เห็นเมนูของระบบส่วนกลางเลย |

ค่าพวกนี้แก้ได้หมดที่ `/core/levels` — ไม่ต้องแก้โค้ด

## สิทธิ์จริงคำนวณยังไง

กฎอยู่ในไฟล์เดียวคือ `src/lib/permissions.ts` (pure function + unit test ที่ `tests/permissions.test.ts`)
และมี view `v_user_permissions` ที่ทำกฎเดียวกันในฐานข้อมูล

```
1. ระดับ admin                                → ได้ทุกสิทธิ์ จบ
2. ไม่มีสิทธิ์เข้าโปรแกรม (เมนู 5 ผู้ใช้งานโปรแกรม) → ไม่มีสิทธิ์ใด ๆ ในโปรแกรมนั้น จบ
3. มีสิทธิ์เฉพาะราย (override)                 → ใช้ค่านั้น
4. ไม่มี                                       → ใช้ค่าเริ่มต้นของระดับ (แม่แบบ)
5. ไม่มีอีก                                    → ไม่มีสิทธิ์
```

**เมนู 5 เป็นประตูด่านแรก**: ให้สิทธิ์เข้าโปรแกรมก่อน แล้วค่อยมากำหนดเมนู/สิทธิ์ที่เมนู 4
คนที่ไม่มีสิทธิ์เข้าโปรแกรมจะไม่แสดงในเมนู 4 และไม่ต้องกำหนดอะไรเลย (migration `0018`)

ในหน้า `/core/users/<id>` แถวที่ติ๊ก **"ตามระดับ"** จะไม่เก็บ override ไว้เลย
ทำให้แก้ค่าที่ระดับทีหลังแล้วมีผลกับคนนั้นทันที — ติ๊กออกเมื่ออยากล็อกค่าเฉพาะคนนี้

## ล็อกอินและการเลือกบริษัท/สาขา

1. `/login` — เบอร์มือถือ + รหัสผ่าน (PIN 4-8 หลัก) เหมือนเดิม
2. ถ้ามีสิทธิ์แค่บริษัทเดียวสาขาเดียว ระบบเลือกให้เองแล้วเข้า `/apps` ทันที
3. ถ้ามีให้เลือกมากกว่าหนึ่ง จะเข้าหน้า `/select-context` — เลือกบริษัทแล้วรายการสาขาจะกรองตามบริษัทนั้น
4. เปลี่ยนบริษัท/สาขาระหว่างวันได้จากปุ่มบนหัวหน้า `/apps`
5. **เปลี่ยนรหัสผ่าน/PIN เองได้จากหน้าล็อกอิน** ที่ `/login/change-pin` (ยืนยันด้วยเบอร์ + รหัสเดิม) โดยไม่ต้องเข้าระบบก่อน

บริษัท/สาขาที่เลือกถูกเก็บไว้ใน JWT ของ cookie เดียวกับ session

# โมดูลที่ 4: ประวัติลูกค้า (`/customers`)

ทะเบียนลูกค้าขององค์กร — ค้นหา เพิ่ม แก้ไข ลบ พร้อมรูปถ่ายและช่องทางติดต่อ
อยู่ในทะเบียนโปรแกรมชื่อ **CUST** จึงกำหนดสิทธิ์ได้เหมือนโปรแกรมอื่นที่ระบบส่วนกลาง

## หน้าจอ

| หน้าจอ | URL | ทำอะไร |
|---|---|---|
| ค้นหา/รายชื่อลูกค้า | `/customers` | ค้นด้วยชื่อ รหัสลูกค้า เบอร์โทร หรือเลขบัตรประชาชน |
| เพิ่มลูกค้าใหม่ | `/customers/new` | รหัสลูกค้าออกให้อัตโนมัติ (C000001, C000002, …) แก้เองได้ |
| ประวัติรายคน | `/customers/<id>` | แก้ไขข้อมูล และลบ (เฉพาะคนที่มีสิทธิ์ลบ) |

## ข้อมูลที่เก็บ

รหัสลูกค้า · ชื่อลูกค้า · เบอร์โทร · ที่อยู่ (ผู้ใช้กรอกเอง) · ตำบล/อำเภอ/จังหวัด/รหัสไปรษณีย์ (ระบบดึงให้)
· รูปถ่าย · เลขที่บัตรประชาชน · วันเกิด · Link Facebook · Link Line · หมายเหตุ

## ที่อยู่ที่ระบบดึงให้อัตโนมัติ

ตาราง `thai_geo` เก็บตำบล/อำเภอ/จังหวัด/รหัสไปรษณีย์ทั่วประเทศ 7,436 แถว จาก 77 จังหวัด
ผู้ใช้พิมพ์ **รหัสไปรษณีย์** (เช่น 71000) หรือ **ชื่อตำบล/อำเภอ/จังหวัด** แล้วเลือกหนึ่งบรรทัด
ระบบเติม ตำบล อำเภอ จังหวัด รหัสไปรษณีย์ ให้ครบเอง (ช่องพวกนี้แก้มือไม่ได้ กันพิมพ์ผิด)

เติมข้อมูลชุดนี้ครั้งแรกด้วย:

```bash
npm run db:geo
```

(รันซ้ำได้ ไม่เพิ่มข้อมูลซ้ำ · ใส่ `-- --force` เพื่อเขียนทับเมื่อมีการยุบ/ตั้งตำบลใหม่)
กรุงเทพฯ ระบบใช้คำว่า **แขวง/เขต** ให้เองแทน ตำบล/อำเภอ

## กฎที่บังคับให้อยู่แล้ว

- **เลขบัตรประชาชน** ตรวจหลักตรวจสอบ (check digit) ไม่ผ่านบันทึกไม่ได้ · ห้ามซ้ำในระบบ (กันบันทึกลูกค้าคนเดิมสองรอบ)
- **เบอร์โทร** เก็บเป็นตัวเลขล้วน กรอกมีขีดหรือไม่มีก็ได้
- **Facebook / Line** ใส่ลิงก์เต็มหรือแค่ชื่อผู้ใช้/LINE ID ก็ได้ ระบบทำเป็นลิงก์กดได้ให้เอง (`@ชื่อ` = บัญชีทางการ)
- **ลบลูกค้า** ต้องติ๊กยืนยัน และลบรูปถ่ายออกจาก storage ให้ด้วยเสมอ

กฎทั้งหมดเป็น pure function ใน `src/lib/customers.ts` มี unit test ที่ `tests/customers.test.ts`

## ตารางในฐานข้อมูล (migration `0014_customers.sql`)

| ตาราง | เก็บอะไร |
|---|---|
| `customers` | ประวัติลูกค้า (`geo_code` อ้างตำบล ไม่เก็บชื่อจังหวัดซ้ำ) |
| `thai_geo` | ตำบล/อำเภอ/จังหวัด/รหัสไปรษณีย์ ทั่วประเทศ |
| `v_customers` | view รวมลูกค้า + ชื่อตำบล/อำเภอ/จังหวัด + ชื่อสาขา |

รูปถ่ายเก็บในถังเดียวกับรูปลงเวลา แต่คนละโฟลเดอร์ (`cust/`) เปิดดูผ่าน `/api/customer/photo` ที่ต้องล็อกอินก่อนเสมอ

## พนักงานที่รับจอง

ช่อง **พนักงานที่รับจอง** บนใบจองเติมชื่อจาก**บัญชีที่ล็อกอินอยู่**ให้อัตโนมัติ และแก้ได้
(หัวหน้าคีย์แทนพนักงานขายได้) เก็บลงฐานข้อมูล 2 ช่องคู่กัน:

| ช่อง | เก็บอะไร |
|---|---|
| `taken_by` | บัญชีผู้ใช้ที่บันทึกใบนี้จริง — ระบบใส่เอง แก้จากหน้าจอไม่ได้ |
| `taken_by_name` | ชื่อพนักงานที่รับจองตามที่แสดงบนใบ — แก้ได้ |

เก็บชื่อไว้ด้วยเพราะบัญชีอาจถูกลบหรือเปลี่ยนชื่อภายหลัง ใบเก่าต้องยังบอกได้ว่าตอนนั้นใครรับจอง
(view `v_bk_bookings` ให้ทั้งสองค่า: `taken_by_name` = ชื่อบนใบ · `taken_by_full_name` = ชื่อบัญชีล่าสุด)

แก้ใบเดิมภายหลังจะไม่เปลี่ยน `taken_by` ให้เป็นคนที่กดแก้ · ชื่อผู้รับจองค้นเจอได้จากช่องคำค้นในหน้า 1.1 และ 1.3

### ลูกค้าดึงจากทะเบียนของระบบขาย (Db2 CUSTMAST)

ช่องลูกค้าบนใบจองไม่ได้ใช้ตาราง `customers` ของระบบนี้แล้ว แต่เลือกจาก **CUSTMAST** ของระบบขาย
ผ่าน popup พิมพ์ค้น (ค้นได้ด้วย รหัสลูกค้า / ชื่อ / นามสกุล / เลขบัตรประชาชน / เบอร์โทร · สูงสุด 50 ราย)

เก็บลง `bk_bookings` เป็น `db2_cuscod` + `db2_customer_name` · เบอร์โทรเติมให้จาก CUSTMAST แก้ทับได้
ใบจองกับสัญญาขายจึงอ้างลูกค้าคนเดียวกันจริง ๆ ไม่ต้องคีย์ซ้ำสองระบบ

ใช้ endpoint `/api/customers` ของแอป Db2 ที่มีอยู่แล้ว (ไม่ต้องแก้ฝั่งนั้น)
view `v_bk_bookings` หยิบชื่อ/รหัสลูกค้าจาก Db2 ก่อน ไม่มีจึงถอยไปใช้ทะเบียนเดิม — ใบเก่ายังอ่านได้ครบ

### รถที่จองดึงจากระบบขาย (Db2)

ช่อง **ยี่ห้อ / รุ่น / แบบ / สี** บนใบจองไม่ได้ใช้ทะเบียน `mc_*` ของระบบนี้แล้ว
แต่ดึงจากข้อมูลหลักของระบบขายจริงผ่านแอป Db2:

| ช่อง | ตารางใน Db2 |
|---|---|
| ยี่ห้อ | `SETTYPE` (TYPECOD, TYPEDES) |
| รุ่น | `SETMODEL` (MODELCOD, MODELDES, **TYPECOD** — ผูกยี่ห้อ จึงกรองรุ่นตามยี่ห้อได้) |
| แบบ | `SETBAAB` (BAABCOD, BAABDES) |
| สี | `SETCOLOR` (COLORCOD, COLORDES) |

ไม่ใช้ dropdown เพราะรุ่นมี ~500 รายการและแบบมีมากกว่านั้น — ใช้ **popup พิมพ์ค้น**
(กดช่อง → เด้ง popup → พิมพ์ → เลือก) แสดงครั้งละ 30 รายการ พร้อมบอกว่าพบทั้งหมดกี่รายการ

เก็บลง `bk_bookings` ทั้งรหัสและชื่อ (`db2_*_code` / `db2_*_name`) — รหัสไว้ map กับสต็อก
ชื่อไว้ให้หน้ารายการแสดงได้โดยไม่ต้องยิงถาม Db2 ทีละแถว
view `v_bk_bookings` หยิบชื่อจาก Db2 ก่อน ไม่มีจึงถอยไปใช้ทะเบียนเดิม — **ใบจองเก่ายังอ่านได้ครบ**

### 1.5 สอบถามสต๊อกรถ (`/booking/stock`)

### Dashboard: ภาพรวมในหน้าเดียว

หน้า 1.4 แบ่งเป็น 2 ชั้น ตัวกรองด้านบนมีผลกับทั้งสองชั้น ต่างกันแค่ช่วงเวลา

**ชั้นบน — ภาพรวมทุกช่วงเวลา** (ไม่จำกัดเดือน)

| การ์ด | ความหมาย |
|---|---|
| ใบจองทั้งหมด | รวมทุกใบ พร้อมยอดปิดงาน/ยกเลิก |
| กำลังดำเนินการ | สถานะเอกสาร = ใช้งาน แยกรอสัญญา/รอรับรถ |
| ปิดการขายได้ | ใบที่มีเลขที่สัญญาขาย + อัตราปิดการขาย (%) |
| รับรถแล้ว | เทียบกับใบที่ยกเลิกไม่รับรถ |
| เงินมัดจำที่ถืออยู่ | มัดจำเฉพาะใบที่ยังไม่จบงาน (เทียบกับมัดจำรวมทุกใบ) |
| รถที่ต้องสั่งเพิ่ม | ใบที่ยังเปิดอยู่และสถานะรถ = ต้องสั่ง |

**อันดับ 5 อันดับแรก + เฝ้าระวังสต็อก** (แถบสัดส่วนเทียบกับอันดับหนึ่ง)

1. รุ่นรถที่จองสูงสุด
2. รุ่นรถที่จองแล้วรถยังไม่มีในสต็อก (เฉพาะใบที่ยังดำเนินการอยู่)
3. พนักงานขายที่รับจองสูงสุด
4. สาขาที่รับจองสูงสุด
5. ใบที่นัดรับรถภายใน 3 วันแต่รถยังไม่มีในสต็อก — **รวมใบที่เลยกำหนดนัดแล้ว** เพราะเป็นใบที่เร่งด่วนที่สุด
6. ใบที่ยกเลิกภายใน 7 วันล่าสุดโดยตอนนั้นรถยังไม่มีในสต็อก — ใช้ `updated_at` เป็นวันที่ยกเลิก
   (ใบจองไม่ได้เก็บวันที่ยกเลิกแยกไว้)

“รถยังไม่มีในสต็อก” นับทั้ง *ต้องสั่ง* และ *สั่งมาแล้ว* เพราะทั้งคู่คือรถที่ยังส่งมอบทันทีไม่ได้
จำนวนเท่ากันเรียงตามชื่อ เพื่อให้ลำดับคงที่ทุกครั้งที่เปิดหน้า

ถัดลงมาเป็น **งานที่ต้องลงมือทำ** 4 กล่อง (แสดง 5 ใบแรก กดเข้าใบจองได้เลย):
เลยวันนัดรับรถ · นัดรับรถวันนี้ · นัดรับรถใน 7 วัน · ยกเลิกแล้วยังไม่คืนเงิน

**รอส่งมอบ — สัญญาผ่านแล้ว + รอรับรถ** 3 การ์ด แยกตามว่ารถอยู่ไหนแล้ว
(งานขายจบแล้ว เหลือแค่รอรถ จึงบอกได้ว่าคอขวดอยู่ขั้นไหน)

| การ์ด | เงื่อนไขที่นับ |
|---|---|
| รถมีในสต็อก | สถานะรถ *มีในสต็อก* + สัญญา *ผ่านแล้ว* + การจอง *รอรับรถ* — นัดรับได้เลย |
| รถที่สั่งมาแล้ว | สถานะรถ *สั่งมาแล้ว* + สัญญา *ผ่านแล้ว* + การจอง *รอรับรถ* — รอรถเข้า |
| รถต้องสั่ง | สถานะรถ *ต้องสั่ง* + สัญญา *ผ่านแล้ว* + การจอง *รอรับรถ* — ยังไม่ได้สั่ง ต้องรีบ |

แต่ละการ์ดบอกจำนวนใบและเงินมัดจำที่ผูกอยู่ กดแล้วเด้งไปหน้าสอบถามที่กรองเงื่อนไขเดียวกันไว้ให้แล้ว
ไม่ต้องกรองสถานะเอกสารซ้ำ เพราะใบที่ยกเลิกจะมีสถานะการจองเป็น *ยกเลิกไม่รับรถแล้ว* อยู่แล้ว

ใต้การ์ดเป็น **รายการที่รอส่งมอบ** พร้อมช่อง **“รอมาแล้ว”** = วันนี้ − วันที่จอง (`daysWaiting()`)
เรียงจากรอนานสุดลงมา · ป้ายเปลี่ยนสีตามความช้า: ต่ำกว่า 14 วันเทา · 14-29 วันเหลือง · 30 วันขึ้นไปแดง
วันที่จองล่วงหน้าคืน 0 วัน ไม่ติดลบ

## ใบจอง vs ใบ Update

- **ใบจอง** = "ตอนนี้เป็นยังไง" — สถานะปัจจุบันอยู่บนใบจองใบเดียว
- **ใบ update** = "ใครเปลี่ยนอะไรเมื่อไหร่" — หนึ่งใบจองมีได้หลายใบ

ช่องสถานะในใบ update เว้นว่าง = **ไม่เปลี่ยน** (คงค่าเดิมของใบจอง) — ตรรกะนี้อยู่ใน `applyUpdate()`
`createUpdate()` เป็นผู้เขียนสถานะใบจองจากหน้าจอ 1.2 เพียงตัวเดียว สถานะสองที่จึงไม่มีวันหลุดจากกัน
เลขที่สัญญาขาย/วันที่ขาย/ธงคืนเงิน แก้ได้จากหน้าจอ 1.2 เท่านั้น (หน้าจอ 1.1 แก้ไม่ได้)

ลบใบ update **ไม่ย้อนสถานะบนใบจองให้อัตโนมัติ** (เดาสถานะก่อนหน้าผิดแล้วเสียหายกว่า) — ให้บันทึกใบใหม่แทน

- กราฟและตารางกว้าง ๆ เลื่อนอยู่ในกล่องของตัวเอง (`overflow-x-auto`) ไม่ดันหน้าให้กว้างเกินจอ

## ยังไม่มีค่าเบื้องต้น? เพิ่มจากหน้าใบจองได้เลย

ช่อง **ชื่อลูกค้า · ยี่ห้อ · รุ่น · แบบ · สี** มีลิงก์ไปหน้าบันทึกค่าเบื้องต้นของตัวเองอยู่ข้างช่อง

1. กดลิงก์ → ระบบจำค่าที่กรอกค้างไว้ทั้งใบ (รวมเอกสารแนบที่อัปโหลดไปแล้ว) ไว้ใน `sessionStorage`
2. พาไปหน้าค่าเบื้องต้นนั้นพร้อมป้ายบอกว่ากำลังเพิ่มเพื่อกลับไปใช้ต่อ (กด “กลับโดยไม่เพิ่ม” ได้)
3. บันทึกเสร็จ ระบบพากลับมาที่ใบจองใบเดิม **เลือกค่าที่เพิ่งเพิ่มให้อัตโนมัติ** และคืนค่าที่กรอกค้างไว้ครบ

กด “+ เพิ่มรุ่น” ตอนเลือกยี่ห้อไว้แล้ว ระบบจะเลือกยี่ห้อนั้นเป็นตัวแม่ให้ล่วงหน้า (แบบรถก็อ้างรุ่นให้เหมือนกัน)
กรอกผิดที่หน้าค่าเบื้องต้นแล้วเด้งกลับมา บริบท “มาจากใบจอง” ยังอยู่ ไม่ต้องเริ่มใหม่

เส้นทางที่เด้งกลับรับเฉพาะ path ภายในเว็บนี้ (`safeReturnPath()`) กัน open redirect —
กฎอยู่ใน `src/lib/form-draft.ts` มี unit test ที่ `tests/form-draft.test.ts`

## อำนาจอนุมัติ 2 ชั้น แยกกันชัดเจน

| ชั้น | คุมอะไร | ตั้งที่ไหน |
|---|---|---|
| สิทธิ์เมนู | เข้าหน้าจอไหนได้ / กดอนุมัติได้ไหม | ระบบส่วนกลาง → สิทธิ์เมนูในโปรแกรม |
| **วงเงินอนุมัติ** | **อนุมัติได้ถึงจำนวนเท่าไร** | **ระบบอนุมัติ → 5. ตั้งค่าอำนาจอนุมัติ** |

**เกินวงเงินทำงานแบบ 2 ชั้น**: หัวหน้าที่วงเงิน 5,000 เจอเรื่อง 20,000 จะกดอนุมัติไม่ได้เลย
(ปุ่มถูกปิดพร้อมบอกเหตุผล) ทำได้แค่ **"เสนอผู้มีอำนาจสูงกว่า"** พร้อมความเห็น →
เรื่องเปลี่ยนเป็นสถานะ *เสนอขึ้นผู้บริหาร* แล้วไปโผล่ในกล่องของผู้บริหารพร้อมความเห็นของหัวหน้า

ลำดับการใช้กฎ (เฉพาะเจาะจงมากกว่าชนะ):
```
1. ระดับ admin                        → ไม่จำกัดวงเงิน ตัดสินขั้นสุดท้ายได้เสมอ
2. กฎเจาะจงคน + เจาะจงประเภทเรื่อง
3. กฎเจาะจงคน (ทุกประเภทเรื่อง)
4. กฎตามระดับ + เจาะจงประเภทเรื่อง
5. กฎตามระดับ (ทุกประเภทเรื่อง)
6. ไม่มีกฎเลย                          → อนุมัติไม่ได้ (ยื่นเรื่องได้อย่างเดียว)
```
กฎผูกบริษัทได้ด้วย (เว้นว่าง = ทุกบริษัท) · แก้กฎแล้วมีผลทันทีกับเรื่องที่ยังรออยู่ ·
หน้าตั้งค่ามี **กล่องทดสอบกฎ** ให้ลองว่า "คนนี้ + เรื่องนี้ + จำนวนนี้" อนุมัติได้ไหม
ก่อนใช้จริง (คำนวณด้วยฟังก์ชันชุดเดียวกับตอนอนุมัติจริง ผลจึงตรงกันเสมอ)

### หน้าตั้งค่าอำนาจอนุมัติ — ตั้งเป็นรายคนก่อน

หน้า `/approvals/setup/limits` เรียงตามลำดับที่ใช้จริง:

1. **ผู้มีอำนาจอนุมัติ** (หลัก) — ขั้นที่ 1 เลือกผู้ใช้ → ขั้นที่ 2 ติ๊กว่าอนุมัติเรื่องใดได้บ้าง
   และใส่วงเงิน/ส่วนลดสูงสุดของแต่ละเรื่อง (เว้นว่าง = ไม่จำกัด · เรื่องที่ไม่มีจำนวนเงิน เช่น ขอสลับกะ
   ติ๊กแล้วอนุมัติได้เลย) · บริษัท / ปฏิเสธได้ / ตัดสินขั้นสุดท้าย ตั้งครั้งเดียวใช้กับทุกเรื่องของคนนั้น ·
   กดบันทึกทีเดียว = หนึ่งแถว `apv_limits` ต่อเรื่องที่ติ๊ก (ล้างของเดิมของคนนั้นแล้วบันทึกตามหน้าจอ)
2. **ผู้มีอำนาจอนุมัติทั้งหมด** — รายชื่อพร้อมป้ายสรุป "💰 ขอเบิกเงิน ≤ 5,000" · กดแก้ไข / ถอนอำนาจได้
3. **วงเงินไม่ต้องขออนุมัติ** — ต่อประเภทเรื่อง (`apv_types.auto_approve_limit`) ยอดที่ไม่เกินนี้
   ระบบอนุมัติให้ทันทีตอนยื่น บันทึกผู้ตัดสินเป็น "ระบบอนุมัติอัตโนมัติ" พร้อมหมายเหตุบอกวงเงินที่ใช้ ·
   ค่าตั้งต้น: **ขอเบิกเงินเดือน ≤ 3,000 บาท ไม่ต้องขออนุมัติ** (แก้ตัวเลขได้จากหน้านี้ · เว้นว่าง = ต้องขออนุมัติทุกใบ) ·
   มีผลทั้งฟอร์มกลาง (`createApprovalRequest`) และใบขอเบิกของโปรแกรม HR (`createAdvanceForm`)
4. **ค่าเริ่มต้นตามระดับการทำงาน** (พับไว้) — ใช้กับคนที่ยังไม่ได้ตั้งเป็นรายคน

## การตัดสินและร่องรอย

ไม่อนุมัติ** (ต้องเลือกเหตุผลจากรายการที่แอดมินตั้งไว้) **· เสนอผู้มีอำนาจสูงกว่า**

จำนวนที่อนุมัติ · เหตุผล · หมายเหตุ · วงเงินที่คนนั้นมีตอนตัดสิน** (ไว้ตรวจย้อนหลังว่าตัดสินในอำนาจจริง)

## จับคู่ผู้ใช้เว็บ ↔ พนักงานขายในระบบขาย (Db2)

รายชื่อฝั่งระบบขายมาจาก **ทะเบียนพนักงาน `ASVSHPV.OFFICER`** ผ่าน endpoint `/api/officers`
ของแอป Db2 (`db2Officers()` ใน `src/lib/db2-api.ts`)

ตรวจกับข้อมูลจริง 7 ก.ย. 2569 ก่อนใช้:

| ประเด็น | ผลตรวจ |
|---|---|
| `OFFICER.CODE` เป็นรหัสเดียวกับ `SALCOD` ไหม | ใช่ — คนที่ขายจริงรอบ 12 เดือนอยู่ในตารางครบ **33/33 รหัส** |
| ทำไมไม่ใช้ `SECRET` (ตารางชื่อที่ war room ใช้) | มีชื่อแค่ 13/33 รหัส · `OFFICER` มีชื่อครบ 302/302 แถว |
| กรองด้วย `DEPCODE` ได้ไหม | **ไม่ได้** — คนที่ขายจริงกระจายอยู่ทั้ง SM(17) AF(10) FN(3) SP(3) กรองแล้วคนขายหายครึ่ง |
| `STATUS` | `Y` ยังทำงานอยู่ · `N` ออกแล้ว — **ฝ่ายบุคคลแก้ค่านี้ระหว่างวันได้** (7 ก.ย. 2569 เช้า Y=88 บ่าย Y=50) |

- หน้าจอจับคู่ดึง **เฉพาะคนที่ยังทำงานอยู่ (`STATUS = 'Y'`)** เท่านั้น ไม่มีปุ่มดูคนที่ออกแล้ว
  และ **แสดงจำนวนคันที่ขายได้ 365 วันกำกับทุกรายการ** เพราะทะเบียนนี้รวมทุกแผนกและมีรายการที่ไม่ใช่คน
  (เช่น `KMS — บริษัท เกรียงไกรมอเตอร์เซลส์ จำกัด`, `IT — Install System`) เรียงคนที่ขายมากสุดขึ้นก่อน
- ข้อยกเว้นเดียว: **รหัสที่จับคู่ไว้อยู่ก่อนแล้ว** จะถูกดึงมาด้วย (`?code=…&status=all`) เพื่อให้แถวนั้น
  ยังแสดงชื่อได้ ติดป้าย "ออกแล้ว" — แต่ไม่ถูกเสนอเป็นตัวเลือกใหม่ให้บัญชีอื่น
- ⚠️ คนที่ลาออกแล้วแต่ยังมียอดขายค้างในรอบปีจะไม่อยู่ใน dropdown (7 ก.ย. บ่ายมี 10 รหัส เช่น
  `MN182` ปิยพร ยิ้มใย 135 คัน · `MN259` ศุภชัย แทนพันธุ์ 48 คัน) — ถ้าจำเป็นต้องจับคู่ ใช้ช่อง
  "พิมพ์รหัสเอง" ได้ตามปกติ
- ระบบเดาคู่ให้อัตโนมัติเมื่อชื่อตรงกันพอดี (ตัดคำนำหน้า `นาย/นาง/นางสาว/น.ส./นส.` และช่องว่างออกก่อนเทียบ
  — สองระบบพิมพ์คำนำหน้าและช่องว่างไม่เหมือนกัน) ทดสอบกับข้อมูลจริงแล้ว **เดาได้ 21 คู่**
  (ตอนใช้ `SECRET` ได้แค่ 9) · ชื่อซ้ำกันหลายรหัสจะไม่เดาให้ ต้องเลือกเอง (กันจับคู่ผิดคน)
- ถ้าแอป Db2 ยังไม่ได้ build ใหม่ (ยังไม่มี `/api/officers`) หน้าจะถอยไปใช้รายชื่อจาก `dims.salesman`
  ของ `/api/wall` ให้อัตโนมัติพร้อมขึ้นแถบเตือน — ใช้งานต่อได้ แค่ชื่อไม่ครบ
- หนึ่ง `SALCOD` จับคู่ได้กับบัญชีเดียวเท่านั้น (unique ทั้ง `employee_id` และ `db2_salcod`)
  ไม่งั้นยอดขายจะถูกนับให้สองคน
- เก็บชื่อที่เห็นตอนจับคู่ไว้ในตารางด้วย (`db2_name`) เพื่อให้หน้าจอยังอ่านออกตอนเครื่องในบริษัทปิด
- คู่นี้ใช้ร่วมกันได้กับระบบรับจอง เพราะทั้งสองระบบอ้างบัญชีเดียวกัน (`employees.id`)

**Dashboard ใช้คู่นี้ยังไง**: ดึง `/api/wall` ช่วงเดียวกับที่เลือก แล้วรวมจำนวนคันของ `SALCOD`
ที่จับคู่ไว้มาแสดงเป็นคอลัมน์ "ขายจริง (คัน)" · ต่อ Db2 ไม่ติดหน้าไม่พัง แค่ขึ้นแถบเตือนสีเหลือง
และตัวเลขงานประจำวันยังถูกต้องตามปกติ (ช่วงกว้างเกิน 400 วันจะข้ามส่วนนี้ไป เพราะ Db2 จำกัดไว้)

โครงเดียวกับระบบแจ้งซ่อม (`/procurement`) เพราะเป็นงานติดตามสถานะแบบเดียวกัน
ต่างกันที่ **รถและลูกค้าดึงจากระบบขาย (Db2) ด้วยเลขตัวถัง** และมีรายการที่ขอเคลมได้หลายรายการต่อใบ

โปรแกรม `CLM` · ทุกหน้าต้องล็อกอิน และตรวจสิทธิ์รายเมนูจากระบบส่วนกลาง (`/core`)

## รถและลูกค้าดึงจากระบบขาย (Db2)

ปุ่ม **"ค้นจากระบบขาย"** ในใบขอเคลมเปิด popup ค้นด้วยคำเดียว เทียบได้ทั้ง
เลขตัวถัง · เลขเครื่อง · เลขที่สัญญา · รหัสลูกค้า · ชื่อ/นามสกุล · เบอร์มือถือ
เลือกหนึ่งคันแล้วระบบเติมให้ครบทีเดียว: เลขตัวถัง เลขเครื่อง ยี่ห้อ/รุ่น/แบบ/สี และชื่อ/ที่อยู่/เบอร์ลูกค้า

- ฝั่งแอป Db2: `GET /api/vehicles?q=&limit=&sold=1` — join `INVTRAN` + `VIEW_SALEALL` + `CUSTMAST`
  (`VIEW_SALEALL` ไม่มี `CUSCOD` จึงโยงกลับ `ARMAST`/`ARFINC`/`ARCRED` และตารางประวัติ `H*`)
- ฝั่งนี้: `db2Vehicles()` ใน `src/lib/db2-api.ts` (server) หรือ proxy `/api/db2/vehicles`
  (client — คุมสิทธิ์ด้วยเมนู `CLM_CLAIM` ใน whitelist ของ `src/app/api/db2/[...path]/route.ts`)
- ตรวจกับข้อมูลจริง 7 ก.ย. 2569: `INVTRAN` 38,767 คัน เลขตัวถังไม่ซ้ำ · `VIEW_SALEALL` 38,701 แถว
  หา `CUSCOD` เจอ 97.2% (ที่เหลือส่วนใหญ่คือรายการส่งเอเย่นต์) · ค้นด้วยเลขตัวถังตอบใน ~0.3 วินาที
- **ค่าที่บันทึกลงใบเป็นสำเนา ณ ตอนบันทึก** (ทั้งรหัสและชื่อ) — ใบเก่าต้องอ่านออกแม้ระบบขายแก้ข้อมูลภายหลัง
  และหน้าจอรายการไม่ต้องยิงถาม Db2 ทีละแถว (เครื่องในบริษัทปิดได้)

**ลูกค้าภายนอก (ข้อ 1.4.9)**: ติ๊ก "ลูกค้าภายนอก" แล้วคีย์เองทั้งหมด —
บังคับกรอก เลขตัวถัง เลขเครื่อง ชื่อ ที่อยู่ และเบอร์โทร (ใบที่ดึงจาก Db2 ไม่บังคับ 3 ช่องหลัง)

## สถานะงานและวันที่ที่ระบบเติมให้

สถานะงาน 6 ค่า: รอติดต่อแจ้งผู้ผลิต → ส่งเรื่องให้ตัวแทนผู้ผลิต → อนุมัติ / ไม่อนุมัติ →
อยู่ระหว่างดำเนินการแก้ไข → แก้ไขเรียบร้อย

บันทึกจากหน้าจอ 1.5 แล้วระบบผลักขึ้นใบขอเคลมให้ในคราวเดียว (`applyClaimUpdate` ใน `src/lib/claim.ts`):

- อนุมัติ / ไม่อนุมัติ → ลง **วันที่แจ้งผลการอนุมัติ** (1.4.21)
- แก้ไขเรียบร้อย → ลง **วันที่ซ่อมเสร็จ** (1.4.22)
- ทั้งสองกรณีเติมเฉพาะตอนที่ใบยังว่าง — ค่าที่คนกรอกเองไม่ถูกทับ
- ช่องที่เว้นว่างในใบ update = ไม่เปลี่ยนของเดิม · ยอด 0 ถือว่าเปลี่ยนจริง (ต่างจากเว้นว่าง)
- ลบใบ update ไม่ย้อนสถานะให้อัตโนมัติ (เดาสถานะก่อนหน้าผิดแล้วข้อมูลเสียหายกว่าเดิม)

**กำหนดเสร็จ** ยึด "วันที่คาดว่าจะซ่อมเสร็จ" จากใบ update ก่อน ไม่มีจึงคิดจากความเร่งด่วน
(1-2 วัน → 2 วัน · 2-5 วัน → 5 วัน · 5 วันขึ้นไป → 10 วัน) แล้วใช้เตือนงานเกินกำหนดใน dashboard
งานที่จบแล้ว (แก้ไขเรียบร้อย / ไม่อนุมัติ) และเอกสารที่ยกเลิก ไม่นับว่าเกินกำหนด

## งานซ่อมในศูนย์บริการ — Job no (ข้อ 1.5.10-1.5.13)

ใบ update มีช่อง **เลขที่ Job no · วันที่เปิด job · วันที่ปิด job · วันที่ส่งมอบงาน/ปิด job**
เก็บ 2 ที่โดยตั้งใจ (แบบเดียวกับสถานะงานและยอดที่ขออนุมัติ):

| ที่เก็บ | ความหมาย |
|---|---|
| `cl_claim_updates` | "ครั้งนี้บันทึกอะไร" — ประวัติว่าใครใส่เลข job / ปิด job เมื่อไหร่ |
| `cl_claims` | "ตอนนี้เป็นยังไง" — ค่าล่าสุด ใช้ค้นหาและแสดงในตาราง/dashboard โดยไม่ต้อง join ใบ update |

- ต่างจากวันที่แจ้งผล/ซ่อมเสร็จตรงที่ **ช่องของ job ใช้กฎ "กรอกมาก็ทับ"** — เลข job เปลี่ยนได้จริง
  (เปิด job ใหม่ให้ใบเดิม) ค่าบนใบขอเคลมจึงเป็น "ล่าสุด" เสมอ · เว้นว่าง = ไม่เปลี่ยนของเดิม
- ระบบตรวจให้ว่า วันที่ปิด job และวันที่ส่งมอบงาน ต้องไม่ก่อนวันที่เปิด job
- กรอกแค่เลขที่ job หรือวันที่ของ job อย่างเดียว ก็ถือว่าใบ update นั้นมีการเปลี่ยนแปลงจริง (บันทึกได้)
- ค้นหาใบขอเคลมด้วยเลขที่ job ได้จากช่องคำค้นของหน้าสอบถาม/รายการ (มี index `idx_cl_claims_job_no`)
- dashboard และหน้าสอบถามมีตัวเลข **"job ที่ยังไม่ปิด"** (เปิด job แล้วแต่ยังไม่มีวันที่ปิด)
  พร้อมรายการ job ที่ค้างเรียงตามวันที่เปิดนานสุดขึ้นก่อน

## เลขที่เอกสารและรูปภาพ

- `cl_next_doc_no('CM', 2569)` → `CM-2569-0001` (ใบขอเคลม) · `CMU-2569-0001` (ใบ update)
  ตัดชุดตามปี พ.ศ. ของวันที่บนเอกสาร
- รูปสูงสุด 10 รูปต่อใบ (ทั้ง 1.4.14 และ 1.5.9) อัปโหลดผ่าน `/api/claim/photo`
  เก็บในถัง `SUPABASE_MEMO_BUCKET` โฟลเดอร์ `claim/` · เปิดผ่าน signed URL อายุ 10 นาที (ต้องล็อกอิน)
- ย่อรูปในเครื่องก่อนส่ง (ด้านยาวสุด 1600px, JPEG 75%) · ลบใบ = ลบไฟล์ในถังก่อนเสมอ
